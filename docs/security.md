# Security notes

For IT reviewers. Every statement below points at the file that implements it. Planifold is a planning tool: it stores accounts, sessions, plans, helper transcripts, plugin settings, an audit log, and API keys for the AI provider. It does not run automations and holds no credentials for the systems its plugins describe (Gmail, Google Sheets, and so on are descriptions in `plugins/*/plugin.json`, nothing more).

## Authentication

Four sign-in methods. All are configured by environment variables read in `server/src/config.ts` and can be combined, except that `SAML_ENFORCE` turns the other three off.

| Method | Enabled by | Implementation |
|---|---|---|
| Local password | `AUTH_LOCAL=true` (default) | `server/src/auth/routes.ts`, `server/src/crypto.ts` |
| OpenID Connect | `OIDC_ISSUER` + `OIDC_CLIENT_ID` (+ `BASE_URL`, required) | `server/src/auth/oidc.ts` via `openid-client` |
| SAML 2.0 | `SAML_IDP_SSO_URL` + `SAML_IDP_ISSUER` + `SAML_IDP_CERT` (+ `BASE_URL`, required) | `server/src/auth/saml.ts` via `@node-saml/node-saml` |
| Trusted header | `AUTH_TRUSTED_HEADER` | `server/src/auth/plugin.ts` |

Accounts can also be created ahead of any sign-in by SCIM provisioning (below); those accounts have no password and sign in through SAML or OIDC.

**Local password.** `POST /api/auth/login` looks the email up, verifies the scrypt hash, and issues a session. Failures return one message for both unknown email and wrong password, and are written to the audit log with the attempted email. `AUTH_LOCAL=false` makes the login route return 403.

**OpenID Connect.** Authorization code flow with PKCE (`S256`), `state`, and `nonce`, all generated by `openid-client`. The flow's state, nonce, and code verifier are stored in the `oidc_flows` table and bound to a cookie `planifold_oidc` (path `/api/auth/oidc`, HttpOnly, SameSite=Lax, Secure per config, 10 minutes). Flows older than 15 minutes are purged when a new one starts. The callback requires an ID token, reads `sub`, `email`, `name`, and `email_verified` from its claims, and falls back to the userinfo endpoint for the last three if missing; no email means sign-in fails. The account is found by `sub` (`users.oidc_sub`). If no account has that subject, an existing account with the same email is linked to it once, unless the provider reports `email_verified: false` (refused) or the account is already linked to another subject (refused). Otherwise a new user gets `OIDC_DEFAULT_ROLE`, or `app_admin` if the email is listed in `OIDC_ADMIN_EMAILS`. Roles are assigned only at first sign-in; later changes are made in Planifold, not by the provider. The `?redirect=` parameter on `/api/auth/oidc/start` is used only if it is a same-site path: one leading slash, no backslashes, no whitespace; anything else falls back to `/`. Plain `http://` issuers are accepted (`allowInsecureRequests`) for local testing; use `https://` in production. The flow is tested against `oauth2-mock-server` (`server/test/oidc.test.ts`), not against any specific vendor.

**SAML 2.0.** Service provider through `@node-saml/node-saml` 5. `GET /api/auth/saml/start` builds a signed-if-configured `AuthnRequest` (HTTP-Redirect binding, deflated), records its id in the `saml_requests` table, records the `?redirect=` target (same-site path rule as OIDC) in `saml_flows` under a random 32-character RelayState, and redirects to `SAML_IDP_SSO_URL`. The identity provider posts the response to `POST /api/auth/saml/callback` (HTTP-POST binding, `application/x-www-form-urlencoded`, parsed by `@fastify/formbody`). That route is the one endpoint that opts out of the same-origin check (route config `allowCrossOrigin`), because the post comes from the identity provider's origin; it relies on the XML signature instead, never on a cookie. Validation, in `validatePostResponseAsync` and `Saml.finish`: the response must carry an `InResponseTo` that matches an id in `saml_requests` issued within 10 minutes, which is then deleted (replay refused); the response signature and the assertion signature must both verify against `SAML_IDP_CERT` (`SAML_WANT_RESPONSE_SIGNED=false` relaxes the outer one; the assertion signature is always required); exactly one assertion; `Conditions` and `SubjectConfirmationData` validity windows with `SAML_CLOCK_SKEW_SECONDS` tolerance (120 s); `AudienceRestriction` must name `SAML_SP_ENTITY_ID`; and the assertion issuer must equal `SAML_IDP_ISSUER` (node-saml checks the issuer of logout messages only, so `Saml.finish` checks it for sign-ins). Encrypted assertions are decrypted with `SAML_SP_PRIVATE_KEY` when set. `SAML_ALLOW_IDP_INITIATED=true` switches `InResponseTo` checking from `always` to `ifPresent`, which accepts unsolicited responses; those are replayable within their validity window by anyone who obtains one, so the default is off. Identity is the NameID (`users.saml_name_id`); on first sight of a NameID, an account with `scim_external_id` equal to it, or with the same email, is linked once, and an account already linked to another NameID refuses it. Email and name come from assertion attributes (`SAML_ATTR_*`), the email falling back to the NameID when it looks like an address. Roles: `app_admin` when the email is in `SAML_ADMIN_EMAILS` or the `groups` attribute names one of `SAML_ADMIN_GROUPS`, else `SAML_DEFAULT_ROLE`, decided at creation and, upwards only, on the first SAML sign-in of an account SCIM created; later sign-ins never change roles. Errors from node-saml are mapped to fixed messages before reaching the sign-in page (`samlErrorMessage` in `server/src/auth/routes.ts`); the raw error goes to the log at `warn`. There is no single logout. Tested against a mock identity provider (`server/test/saml.test.ts`: signed flow, replay, tampering, wrong key, wrong audience, wrong issuer, expiry, unsigned assertion, unsolicited response, linking, enforcement), not against a live vendor.

**SAML enforcement.** `SAML_ENFORCE=true` (only valid with SAML configured) sets `auth.local=false` and drops the OIDC and trusted-header configuration in `loadConfig`, so `/api/auth/login` and `/api/auth/setup` return 403 and the sign-in page offers only SAML. Sessions record their origin in `sessions.via` (`local`, `oidc`, `saml`); at startup with enforcement on, every session whose `via` is not `saml` is deleted (`purgeSessionsNotVia`), and `findSessionUser` refuses such sessions afterwards. Recovery from a broken identity provider is operational: unset the variable and restart.

**Trusted header.** For an authenticating proxy (oauth2-proxy, Cloudflare Access, Pomerium). On each request without a valid session cookie, the server reads the header named by `AUTH_TRUSTED_HEADER`. If `AUTH_TRUSTED_PROXY_TOKEN` is set, the request must also carry `X-Planifold-Proxy-Token` with that exact value or the header is ignored. Without the token, anyone who can reach the port can pick their identity, so the port must be reachable only from the proxy. Unknown emails become users with `AUTH_TRUSTED_DEFAULT_ROLE`. No session cookie is issued on this path; the proxy re-asserts identity on every request. The token comparison is a plain string comparison, not constant-time.

**Linking and temporary passwords.** When an existing account is linked to an OIDC subject or a SAML NameID, its `must_change_password` flag is cleared, because `POST /api/auth/password` refuses any account whose `auth_source` is not `local`; leaving the flag set would present a demand the person could never satisfy. The change-password gate in the web app is likewise scoped to local accounts (`RequireAuth` in `web/src/App.tsx`).

**Identity key.** Local password and trusted-header sign-in identify a user by lowercased email. OpenID Connect identifies by the provider's subject, SAML by the NameID, SCIM by the account id it was given (with `externalId` as the client's own key); the email is used once, to create the account or to link an existing one (for OIDC, only with a verified address; see above).

**First administrator.** Either `POST /api/auth/setup` (works only while the `users` table is empty and `AUTH_LOCAL` is on; `/api/auth/config` reports `needsSetup` under the same condition) or `BOOTSTRAP_ADMIN_EMAIL` + `BOOTSTRAP_ADMIN_PASSWORD` (at least 10 characters; the account is created with `must_change_password` set). See `bootstrap()` in `server/src/app.ts`. With single sign-on only, the first administrator is whoever is named in `OIDC_ADMIN_EMAILS` or `SAML_ADMIN_EMAILS` / `SAML_ADMIN_GROUPS`.

## SCIM provisioning

`server/src/scim/`. A SCIM 2.0 server at `/api/scim/v2` for Users and Groups, plus `ServiceProviderConfig`, `ResourceTypes`, and `Schemas`.

- **Authentication.** `Authorization: Bearer <token>` only; the session cookie is ignored on these routes, and a missing or wrong token gets 401 with `WWW-Authenticate: Bearer`. Tokens are created by an `app_admin` (`POST /api/admin/scim/tokens`), shown once, and stored as SHA-256 hashes in `scim_tokens` with a label and an 13-character prefix for display (`server/src/scim/tokens.ts`). Lookup is by hash, followed by a `timingSafeEqual` comparison; the token itself is 32 random bytes, base64url, behind a `pcw_scim_` prefix. Revoking deletes the row. There is no expiry; rotate by creating a new token, updating the client, and revoking the old one. `last_used_at` is updated at most once a minute.
- **Origin check.** SCIM routes opt out of the same-origin check (`allowCrossOrigin`) because they are not cookie-authenticated; there is nothing for a cross-site request to ride on.
- **What a token holder can do.** Create accounts (no password, `auth_source` `scim`, `SAML_DEFAULT_ROLE`, or `app_admin` when the email is in `SAML_ADMIN_EMAILS`), read every account (email, name, active flag, external id, group membership; never password hashes or sessions), change any account's email, name, external id, and active flag, delete any account (with its plans), and manage groups. It cannot change roles, read plans, or touch settings. Deactivating an account (`active: false`) sets `disabled` and deletes its sessions, so it takes effect on the next request. A SCIM token is therefore as sensitive as an administrator's session for account lifecycle; treat it as a secret and keep the endpoint behind TLS.
- **Input.** Bodies are validated with zod (`UserBody`, `GroupBody`, `PatchBody` in `server/src/scim/routes.ts`); unknown attributes are accepted and ignored. `userName` (or a primary email) must be an email address, since accounts are keyed by email. Filters are one `attribute eq "value"` clause; anything else is a 400 `invalidFilter`. Group members must be ids of existing users. Page size is capped at 500.
- **Audit.** Every mutation is written to the audit log with `actor_email` `scim:<token label>` and `details.via = "scim"`; token creation and revocation are audited under the administrator.
- **Errors** use the SCIM error schema (`urn:ietf:params:scim:api:messages:2.0:Error`) with `status`, `scimType` (`uniqueness`, `invalidValue`, `invalidFilter`, `invalidPath`, `noTarget`, `invalidSyntax`), and `detail`.

## Sessions

Implemented in `server/src/auth/session.ts`.

- Cookie name `planifold_session`. Value is 32 random bytes from `crypto.randomBytes`, base64url. Attributes: `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` when `SECURE_COOKIES` is true (default: true when `BASE_URL` starts with `https://`), `Max-Age` = `SESSION_DAYS` × 86400 (default 14 days).
- Server side: a row in the `sessions` table (`id`, `user_id`, `created_at`, `expires_at`, `user_agent`, `via`). `via` records how the session was established (`local`, `oidc`, `saml`). Every request looks the cookie up in the database. An expired session, one whose user is disabled, or, with `SAML_ENFORCE`, one whose `via` is not `saml`, is deleted on access. Expired rows are also purged at startup, and so are non-SAML rows when SAML is enforced. Expiry is fixed from creation; there is no sliding renewal.
- Invalidation: logout deletes that session. An administrator disabling a user or resetting their password deletes all of that user's sessions, and so does a SCIM client deactivating the user. Deleting a user cascades to their sessions. A user changing their own password does not end their other sessions.
- If `Secure` is on and the app is reached over plain HTTP, browsers drop the cookie and sign-in appears to do nothing. Either terminate TLS in front or set `SECURE_COOKIES=false` for a non-TLS test.

## Origin check

In `server/src/auth/plugin.ts`, before session lookup. For any request whose method is not `GET`, `HEAD`, or `OPTIONS`: if an `Origin` header is present, it must parse as a URL and its host must equal the request `Host` header or the host of `BASE_URL`; otherwise the request gets 403. An unparseable `Origin` and the literal `null` are rejected. Requests with no `Origin` header pass (they still need the session cookie). The check does not depend on the request path, so percent-encoded paths cannot skip it; the two exemptions are declared on the matched route (`config.allowCrossOrigin`): the SAML assertion consumer, which the identity provider's page posts to and which authenticates by XML signature, and the SCIM endpoints, which authenticate by bearer token. Neither honours the session cookie. There are no CSRF tokens; protection is `SameSite=Lax` plus this check.

## Password hashing

`server/src/crypto.ts`:

- `scrypt` from `node:crypto` with `N = 16384`; `r` and `p` are Node's defaults (8 and 1). 16-byte random salt, 64-byte output.
- Stored as `scrypt$16384$<salt>$<hash>` (base64url). Verification uses `timingSafeEqual`.
- Password length 10 to 200 characters; no other composition rules. Accounts created by an administrator, and the bootstrap administrator, must change their password at first sign-in.
- Temporary passwords (`temporaryPassword()` in `server/src/auth/users.ts`) are four words and a number chosen with `Math.random`, not a cryptographic generator. They are returned once in the API response and must be changed at first sign-in.
- When the email does not exist, scrypt is not run, so a wrong-email response is faster than a wrong-password response. This allows user enumeration by timing.

## API keys for AI providers

`SecretBox` in `server/src/crypto.ts`:

- AES-256-GCM. The key is `scrypt(APP_SECRET, "piecewise-secretbox", 32)`. A fresh 12-byte IV per value. Stored as `v1.<iv>.<tag>.<ciphertext>` in `llm_providers.api_key_enc`.
- `APP_SECRET` comes from the environment. If unset, the server generates 32 random bytes and writes them to `DATA_DIR/.app-secret` with mode `0600` (`loadOrCreateSecret` in `config.ts`).
- The API never returns a key. `publicProvider()` in `server/src/admin/routes.ts` returns `hasKey` and `keyHint`, which is `••••` plus the last four characters (`maskSecret`). The audit entry for a key change records `"(changed)"`.
- Changing `APP_SECRET` makes stored keys undecryptable. The admin page shows `(unreadable: APP_SECRET changed)` and Plani reports the problem; re-enter the key.
- The OIDC client secret, the proxy token, and the SAML signing key live only in the environment (or in files named by `_FILE` variables), not in the database. SCIM tokens are in the database as SHA-256 hashes only.

## Roles

`Role` in `server/src/db/models.ts`; `requireRole` in `server/src/auth/plugin.ts` ranks them `user < integration_admin < app_admin`, so a higher role can do anything a lower one can.

| Role | May |
|---|---|
| `user` | Create, edit, delete, hand off their own plans; use Plani on them; read the catalog; change their own password. |
| `integration_admin` | All of the above, plus edit guidance, access notes, and hidden objects/actions/operations for plugins where they are the recorded owner (`PATCH /api/integrations/:id`). Cannot enable, disable, or reassign a plugin. |
| `app_admin` | Everything under `/api/admin/*`: users, AI providers and keys, organization settings, plugin enablement and ownership, reload, audit log. Reads and edits any plan (`loadPlanFor` in `server/src/plans/access.ts`) and lists all plans with `GET /api/plans?all=1`. Cannot remove their own admin role, disable, or delete their own account. |

Endpoints and the minimum role they need:

| Endpoint | Minimum role |
|---|---|
| `GET /api/health`, `GET /api/auth/config` | none |
| `POST /api/auth/setup` (only while no users exist), `POST /api/auth/login`, `POST /api/auth/logout` | none |
| `GET /api/auth/oidc/start`, `GET /api/auth/oidc/callback` | none |
| `GET /api/auth/saml/start`, `POST /api/auth/saml/callback`, `GET /api/auth/saml/metadata` | none |
| `/api/scim/v2/*` | a SCIM bearer token (never a session) |
| `GET /api/auth/me`, `POST /api/auth/password`, `GET /api/catalog`, `GET /api/helper/status` | `user` |
| `GET`/`POST /api/plans`; `GET`/`PATCH`/`DELETE /api/plans/:id`; `/api/plans/:id/pieces...`; `/api/plans/:id/handoff`; `/api/plans/:id/helper`; `/api/plans/:id/brief` | `user` (plan owner) or `app_admin` |
| `GET /api/integrations` | `user` (shows only plugins the caller owns; all for `app_admin`) |
| `PATCH /api/integrations/:id` | `integration_admin` who owns the plugin, or `app_admin` |
| `/api/admin/*`, including `GET /api/admin/auth` and `POST`/`DELETE /api/admin/scim/tokens` | `app_admin` (enforced by an `onRequest` hook scoped to the admin route plugin in `server/src/admin/routes.ts`, so it applies however the path is encoded) |

`GET /api/health` is unauthenticated and returns the version, plugin counts, and the active provider's label, kind, and model name.

## Audit log

Written by `audit()` in `server/src/db/models.ts` to the `audit_log` table (`actor_id`, `actor_email`, `action`, `target`, `details` as JSON, `created_at`). Read with `GET /api/admin/audit?limit=N` (default 100, maximum 500, newest first). There is no delete, export, or retention endpoint. Actions recorded, from the `audit(` calls in `server/src`:

| Action | When | Details stored |
|---|---|---|
| `setup.bootstrap` | first admin created from env | email |
| `setup.completed` | first admin created via `/setup` | — |
| `login.succeeded` | password, OIDC, or SAML sign-in | `via: oidc` or `via: saml` (with `solicited`) |
| `login.failed` | wrong email or password; OIDC refused (unverified email, subject mismatch); SAML refused (NameID mismatch) | target = attempted email; `via`, `reason` for OIDC and SAML |
| `password.changed` | user changed own password | — |
| `user.created` | admin created a user, first OIDC or SAML sign-in, or a SCIM `POST /Users` | email, role (`via: oidc`, `saml`, or `scim`; `active` for SCIM) |
| `user.linked` | an existing account was linked to an OIDC subject or a SAML NameID | `via`; `role` when a provisioned account was promoted at first sign-in |
| `user.updated` | admin changed name/role/disabled or reset a password; SCIM `PUT` or `PATCH` | the fields changed; never the password (`via: scim`, `method`, `active` for SCIM) |
| `user.deleted` | admin or SCIM client deleted a user | email (`via: scim` for SCIM) |
| `group.created` / `group.updated` / `group.deleted` | SCIM group push | `via: scim`, display name, member count |
| `scim.token.created` / `scim.token.revoked` | admin managed SCIM tokens | label; never the token |
| `provider.created` / `provider.updated` / `provider.activated` / `provider.deleted` | AI provider changes | kind, model, label; `apiKey: "(changed)"` |
| `settings.updated` | org name, guidance, preferred builder | the keys changed, not the values |
| `plugin.updated` | admin changed a plugin's settings | the patch body (including guidance text) |
| `plugins.reloaded` | admin reloaded manifests | counts |
| `integration.updated` | integration admin changed their plugin | the patch body |
| `plan.created` / `plan.status` / `plan.deleted` | plan lifecycle | status / title |

Not audited: reads (including SCIM reads), piece edits, helper messages (these are stored in `helper_messages`, per plan), logouts, provider tests, OIDC and SAML callback failures other than the refusals above (logged at `warn` level only), and SCIM requests with a bad token (401, not logged).

## Rate limits

`@fastify/rate-limit`, keyed by client IP (`req.ip`, which honours `TRUST_PROXY`). The store is in-memory: per process, reset on restart. Values from `server/src/app.ts` and the route options:

| Scope | Limit |
|---|---|
| All routes | 600 requests per minute |
| `POST /api/auth/setup` | 5 per minute |
| `POST /api/auth/login` | 10 per minute |
| `POST /api/auth/saml/callback` | 20 per minute |
| `POST /api/plans/:id/helper` | 30 per minute |
| `POST /api/plans/:id/brief` | 10 per minute |

Limits are off when `NODE_ENV=test`. Request bodies are capped at 1,000,000 bytes (`bodyLimit`). Behind a reverse proxy with `TRUST_PROXY=false`, every client shares the proxy's IP and therefore one bucket. There is no account lockout.

## HTTP headers

Set in an `onSend` hook in `server/src/app.ts` on every response:

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: same-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Responses outside `/api/` also get:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

`'unsafe-inline'` applies to styles only. Responses under `/api/` get `Cache-Control: no-store`; files under `/assets/` get a one-year immutable cache. The server does not set `Strict-Transport-Security`; set it at the TLS terminator.

## What leaves the server

Planifold makes outbound requests in two cases only.

1. **The configured model provider**, when an administrator has activated one (`server/src/helper/service.ts`, `server/src/helper/providers/*`). Destination is the provider's default endpoint (`api.anthropic.com`, `api.openai.com`) or the `baseUrl` set for that provider. What is sent, built in `server/src/helper/prompt.ts`:
   - The system prompt: Plani's instructions, the full catalog of enabled plugins (ids, objects, fields, actions, operations, each plugin's guidance and access notes), the organization name, organization guidance, and the preferred builder. For Anthropic this block is marked for the provider's prompt cache (`cache_control: ephemeral`).
   - The plan state: title, the thought, remembered facts, every piece's sentence, notes, open blanks, and grammar observations.
   - The last 12 helper messages for that plan and the person's current message.
   - For the build brief: the rendered handoff Markdown plus organization guidance.
   - For "Test connection": the fixed string `Reply with the single word OK.`
2. **The OIDC issuer**: discovery, token exchange, and userinfo, when OIDC is configured.

SAML adds no outbound request: the browser carries the request to the identity provider and the response back. SCIM is inbound only, from the identity provider to `/api/scim/v2`.

No telemetry, no update check, no third-party assets in the web app (fonts are bundled; `connect-src 'self'`). The Quadlet unit in `deploy/planifold.container` sets `AutoUpdate=registry`, so Podman, not the app, polls `ghcr.io` for new images. Logs go to stdout via pino: request method, URL, and client address; error messages; never request bodies or keys.

The model has no tools and cannot reach any system. Its answer is a JSON object validated against a schema, and every suggested slot value is re-checked by the grammar (`applySuggestion` in `server/src/helper/apply.ts`): unknown ids are dropped, references must point at existing pieces, free text is accepted only where the slot allows it. Plan text, plugin guidance, and organization guidance all reach the model as prompt content, so any of them can steer it; that is by design and is why plugin directories should be treated as trusted configuration.

## Plugin trust model

`server/src/plugins/registry.ts` and `shared/src/manifest.ts`.

- A plugin is a directory containing `plugin.json` and optionally `README.md`. The manifest is read with `JSON.parse` and validated with the zod schema in `shared/src/manifest.ts`; the `id` must equal the directory name. Invalid plugins are skipped and listed under "problems" in the admin UI and `/api/health`.
- Manifests are declarative: objects, fields, actions, operations, and text (`description`, `guidance`, `setup.notes`, `setup.docsUrl`). The server never `require`s or executes anything from a plugin directory. There are no hooks or lifecycle scripts.
- Manifest text is shown in the UI and included in the model prompt (see above). The README is rendered by the app's own Markdown subset (`web/src/lib/markdown.tsx`), which builds React elements and never injects HTML. `setup.docsUrl` is an unvalidated string rendered as a link on the admin plugin page.
- Built-in plugins ship in the image. Extra plugins come from `PLUGINS_DIR` (`/plugins` in the container; `compose.yaml` mounts `./plugins-extra` there read-only). Reloading is an `app_admin` action and is audited. `npm run validate-plugins` runs in CI.

## Storage and file permissions

- One SQLite database at `DB_PATH` (default `DATA_DIR/planifold.sqlite`), opened in WAL mode, so `-wal` and `-shm` files sit beside it. It holds everything: password hashes, sessions, plans and pieces, helper transcripts, encrypted API keys, plugin settings, the audit log, OIDC and SAML flow state, hashed SCIM tokens, and SCIM groups.
- `better-sqlite3` creates the file with the process umask; the code sets no explicit mode. `DATA_DIR` is created with `mkdirSync` if missing, also under the umask. Only `.app-secret` is written with mode `0600`.
- In the container the process runs as the unprivileged `node` user and `/data` is owned by it (`Containerfile`). On the host, restrict `DATA_DIR` to the service user (for example `chmod 700`).
- `.gitignore` excludes `data/`, `*.sqlite*`, and `.env*` except `.env.example`.

## Known limitations

- SQLite on one node. Sessions and OIDC flows are in the database and could be shared, but the rate-limit store and the catalog cache are per process, so a second instance would not see plugin-setting changes made in the first until it reloads.
- No TLS in the app. No HSTS header.
- No CSRF tokens; `SameSite=Lax` plus the Origin check.
- No multi-factor authentication of its own; use an OIDC provider that enforces it.
- No password composition rules and no account lockout; only the per-IP rate limit.
- Login timing reveals whether an email exists.
- Temporary passwords use `Math.random`.
- The proxy token check is not constant-time.
- A user's own password change leaves their other sessions valid.
- OIDC: no RP-initiated logout, no group or role claim mapping, tested only against a mock provider. An existing local account is linked to an OIDC subject on first sign-in by email; providers that never send `email_verified` are trusted on that point.
- SAML: no single logout; roles come from `SAML_ADMIN_EMAILS` / `SAML_ADMIN_GROUPS` at creation (or first sign-in of a provisioned account) only, with no ongoing group-to-role sync; an existing local account is linked by email on first sign-in, trusting the identity provider on ownership of the address; IdP-initiated sign-in, when enabled, is replayable within the assertion's validity window; tested against a mock identity provider, not a live one; metadata is unsigned.
- SCIM: tokens do not expire and there is no per-token scope (every token can do everything SCIM can); `DELETE /Users/:id` removes the account and its plans; no bulk operations, sorting, ETags, or `attributes` projection; group membership does not affect roles.
- The audit log has no retention or export.
- `/api/health` is public and names the active model.
- Plani's rule-based fallback (`server/src/helper/fallback.ts`) is limited; it does not send data anywhere, but it also does not replace a model.

## Recommendations

1. Put Planifold behind a TLS-terminating reverse proxy. Set `BASE_URL` to the `https://` address so cookies are `Secure` and the origin check has a fixed host, and set `TRUST_PROXY=true` so rate limits apply per client. Add `Strict-Transport-Security` at the proxy.
2. Set `APP_SECRET` explicitly (`openssl rand -base64 32`) and keep it in your secrets store, not only in `DATA_DIR`. Rotating it requires re-entering every provider key.
3. Once single sign-on works, set `AUTH_LOCAL=false`, or with SAML set `SAML_ENFORCE=true`, which also ends every non-SAML session. Put your administrators in `OIDC_ADMIN_EMAILS` or `SAML_ADMIN_EMAILS` before their first sign-in. Leave `SAML_ALLOW_IDP_INITIATED` off unless people need to start from the Okta dashboard.
4. Use trusted-header sign-in only with `AUTH_TRUSTED_PROXY_TOKEN` set and the port reachable only from the proxy.
5. Treat SCIM tokens as administrator secrets: one per client, labelled, stored in the identity provider only, revoked when the client goes away. Review the audit log for `scim:` actors after enabling provisioning.
6. Back up `DATA_DIR` (database, WAL files, and `.app-secret` if generated). Stop the container or use SQLite's backup command for a consistent copy.
7. Restrict `DATA_DIR` to the service user. Mount `PLUGINS_DIR` read-only and review manifests before enabling them.
8. Choose a model provider whose data-handling terms cover the plan text your users will write, since that text is sent to it.

## Reporting a vulnerability

Report privately through GitHub Security Advisories for `christag/planifold`, not in a public issue. `SECURITY.md` in the repository root lists what to include, what is out of scope, and what to expect: a best-effort project with no security team, aiming to acknowledge within a week, supporting only the latest commit on `main`.
